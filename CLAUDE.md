## Code architecture (web/src)

Layered like a separate server + UI, inside one Next.js app. Full detail: `web/ARCHITECTURE.md`; API/action/page contract: `web/CONTRACT.md`; design tokens and components: `ui/DESIGN.md`. Backup of the pre-refactor tree: `yedek/web-onceki-mimari-2026-10-16.tar.gz`.

- `app/`: routing shell only. `page.tsx` files are thin (metadata + the component from `features/`); `app/api/*/route.ts` are one-line re-exports of `server/routes/*`. Keep `error.tsx`, `not-found.tsx`, `loading.tsx`, `layout.tsx` here.
- `features/<name>/`: per-feature UI (`<Name>Sayfasi.tsx`), Server Actions (`actions.ts(x)`), feature components. Features: kesif (home), cv, ilan-analiz, takvim, kaynaklar, rehber, hakkinda, gizlilik, profil, firsatlar, firsat-detay, laboratuvarlar, hocalar, basvurular, aramalar, yonetim, auth, hata-bildir.
- `layout/` (UstMenu, AltBilgi, NavLink) and `components/ui/` (Card, Badge, Button, ProgressBar, SectionHeader; domain-free). Styles: `styles/tokens.css`, `efektler.css`, `uyarlama.css`; `app/globals.css` only imports them.
- `server/`: never imports UI. `routes/` (API handlers wrapped with `api()` from `http.ts`, tests beside them), `middleware/` (`rbac.ts`: `kullaniciId`, `adminMi`, `adminZorunlu`; `cron.ts`; `erisim.ts`: which paths need a session, used by `proxy.ts`), `lib/` (domain logic, `ai/`, `supabase/`), `errors.ts` (`HttpHatasi` subclasses). Unknown errors become a generic 500; errors with a `digest` (Next control flow) are rethrown by `api()`.
- Dependency direction: `app → features → layout/components/server → db`. Put logic in `server/lib` as pure, tested functions; pages only compose.
- Next 16 build gotchas: client hooks that read the URL (e.g. `usePathname` in `NavLink`) must sit inside `<Suspense>`; data-fetching components too. Always run `npm run build` after structural changes (dev mode does not catch these).
- `./start.sh` starts the dev server.

## Product in one paragraph

A tool for university students (first release: computer/electronics engineering, Turkey) to find internships and research opportunities. The loop is: enter a profile, see matching listings and research groups, check eligibility, get an email draft, track the application. It differs from competitors by also surfacing labs and academics that post no listings, and by showing a source and last-checked date for every fact.

## Architecture principles from the plan

- **Provenance is the core invariant.** Every claim about an opportunity, institution or person links to a `Kaynak` (source) and `Doğrulama` (verification) record with a URL, check date and method. Don't build features that bypass this. Provenance is part of the data model, not a UI add-on.
- **Unverifiable means unknown.** Opportunity status is `açık / kapalı / bilinmiyor`. A listing unchecked for more than 30 days, or past its deadline, becomes "bilinmiyor" or "kapalı". Lab student-intake defaults to "bilinmiyor". When two sources disagree, show both and warn the user.
- **LLM output needs a quote.** Every requirement the LLM extracts is stored with the sentence it quotes from the source text, and claims without a quote are never shown. Rankings and explanations are cached and recomputed only when the profile or opportunity changes.
- **Matching pipeline, in order.** (1) Hard filters in code: city/remote, period, deadline, status. (2) Vector search in pgvector over interests vs. listing descriptions, group topics and publication abstracts, taking the top 30–50. (3) LLM ranking and explanation, returned as structured JSON with source quotes. Don't hand matching wholly to the LLM.
- **Eligibility analysis.** Listing requirements are extracted once into the `Şart` table, then compared per user and labelled karşılanıyor / eksik / doğrulanmalı.
- **Email drafts.** Use only skills with evidence (`Beceri.kanıt`) and research areas that exist in the `Doğrulama` table. Drafts are editable text, and **the system never sends email on the user's behalf**.

## Planned stack

TypeScript with Next.js and Tailwind, PostgreSQL with pgvector (e.g. Supabase), Prisma or Drizzle, the Claude API for ranking, explanation, requirement extraction and drafts, and a multilingual embedding model (Turkish profiles vs. English abstracts). Data collection runs as Python scripts (OpenAlex, ORCID, page fetching). The plan notes a pure-Python alternative (FastAPI) depending on the author's language preference. Confirm the choice before scaffolding.

## Data-collection constraints

- LinkedIn, Kariyer.net and similar platforms forbid scraping. Process only links the user pastes. Company career pages are crawled with robots.txt respected.
- Record each source's terms of use. Verify program conditions and access permissions (especially bulk access to YÖK Akademik) at the official pages before collecting.
- Prefer open APIs (OpenAlex, ORCID, Crossref, DergiPark), official department pages, and a small hand-verified core dataset (3–5 universities for lab discovery in the MVP).
- Store an academic's email address only if it is published on an official page.
- Personal data (CV, GPA) is subject to KVKK: minimise it, get explicit consent, and support deleting the account and its data.

## Phasing

MVP: profile, matching and explanation, eligibility analysis, source/verification records, email drafts, application tracking, and narrow lab discovery. Phase 2: professor search by research topic, gap-closing roadmap, alternative opportunity finder, saved searches and notifications. Phase 3: automatic scheduled crawling and re-verification. Phases advance on criteria rather than dates (e.g. at least 10 of 20 real students applied to a recommended opportunity).
